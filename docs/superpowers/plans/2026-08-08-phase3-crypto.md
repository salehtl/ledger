# Phase 3 — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Bank mail and transactions are encrypted before they are stored. The server holds ciphertext and cannot read it. The user's existing plaintext history is migrated, not discarded.

**Read the spec first:** `docs/superpowers/specs/2026-08-08-phase3-crypto.md`. It records why the onboarding copy will not say "only you can access it", and three alignment items for the operator.

## The rule that governs every task

**There must never be a half-encrypted log.** Tasks are ordered so that stopping between any two leaves a working plaintext system, not a broken hybrid. Do not begin sealing until key material and recovery both work; do not migrate until sealing works.

## Global Constraints

- **Do not weaken any existing safety property**: the unknown-newer-version hard stop, the writer proof-of-possession, the trust path never reading configuration, the single op author.
- **`SCHEMA_VERSION` stays 3.** Sealing changes the blob envelope, not the op schema. If a task appears to need an op change, stop and report.
- Money is `bigint`; never `Number` for an amount.
- Design aesthetic FROZEN: compose from `web/src/components/`; read `web/src/components/README.md` first; 44px targets, 16px inputs.
- Motion: `lib/motion.ts` is the sole source of durations/curves; `m.*` never bare `motion.*`; tests rendering `m.*` wrap in `MotionProvider`.
- Never import `@ledger/client/platform` or `@ledger/client/store/open` from browser code.
- The git index is shared: stage and commit in ONE atomic command with explicit paths from the repo root.
- **Do not run `cd web && bun run build`** — it writes the tracked `internal/v2/webui/dist` artifact the deploy step owns.
- **Every string about encryption must be literally true.** This is a privacy claim to people signing a consent document. If you cannot make a sentence true, write the weaker one and say so in your report.
- Commit with a `Co-Authored-By: Claude` trailer.

### Task 1: Key material and recovery

**No data path changes.** At the end of this task the system still stores plaintext; it simply has keys and a recovery phrase.

**Files:** `client/src/crypto/` (new), `web/src/v2/keys.ts` (new), the onboarding recovery step, `internal/v2/api/keys.go` (new) + migration. Tests alongside.

- [ ] **Step 1:** Read `client/src/platform.ts`'s seam and `client/src/platform.web.ts`. All crypto primitives must go through the platform seam or be added to it — do not reach for `crypto.subtle` directly in engine code, because the seam is what keeps Bun and the browser in step.
- [ ] **Step 2:** Generate, per account: an **X25519 ingest keypair** (the server seals to the public half) and an **AES-256-GCM DEK** (for client-authored blobs). Publish only the public key.
- [ ] **Step 3:** **Wrap both keys under a recovery phrase.** High-entropy, generated by us, from a standard wordlist. The wrapped blob is stored server-side and is opaque to the server. Argon2id or HKDF as appropriate — justify the choice and the parameters in the report.
- [ ] **Step 4:** Store the unwrapped keys as **non-extractable `CryptoKey` handles in IndexedDB**. The private material must never be readable from JavaScript after this point. Verify that: attempt an export in a test and confirm it throws.
- [ ] **Step 5: the recovery phrase is mandatory and confirmed.** Onboarding generates it, shows it, and requires the user to confirm they have recorded it before continuing. **Do not offer a "skip" — on the web there is no Keychain, and skipping means an unrecoverable account.** The copy must say exactly that.
- [ ] **Step 6:** Recovery works end to end: a browser with cleared storage, given the phrase, recovers the keys and reads existing data. Test it as a fresh device, not as a unit.
- [ ] **Step 7:** Server-side storage for the public key and the wrapped blob. Mirror `00003_writers.sql`'s grant recipe — the two easily-missed steps fail only in production.
- [ ] **Step 8:** Commit.

### Task 2: Sealing at ingest

**Files:** `internal/v2/blob/` (a real `Sealer`), `internal/v2/ingest/`, `client/src/wire/blob.ts`. Tests alongside.

- [ ] **Step 1:** Implement HPKE sealing to the user's X25519 public key, in the `encv2.go` envelope shape — `[1B version=2][2B aadLen][aad][32B enc][12B nonce][sealed][16B tag]`. Read that file's header first: it is a benchmark instrument and says so, and it names the two design questions the spec has now settled.
- [ ] **Step 2:** **The AEAD binds the whole cleartext header**, not the embedded AAD alone (spec decision 2, `blob.go`'s own argument, same cost).
- [ ] **Step 3:** The TypeScript opener must reproduce the Go sealer exactly. Add cross-language conformance vectors, in the shape the existing normalizer conformance suite uses — a disagreement between the two must fail the build.
- [ ] **Step 4:** An account **without** published keys must continue to work in plaintext. This is what keeps a partial rollout safe and lets the migration be staged.
- [ ] **Step 5:** Verify by construction: seal a real corpus message, confirm the stored bytes contain no plaintext (grep the ciphertext for a known merchant string), and confirm the client opens it to exactly the original.
- [ ] **Step 6:** Commit.

### Task 3: Client-authored blobs

**Files:** `client/src/wire/blob.ts`, `client/src/outbox/`. Tests alongside.

- [ ] **Step 1:** Client-authored op blobs are sealed under the **DEK**, not HPKE — the client holds the key, so there is no need for a per-record ephemeral.
- [ ] **Step 2:** AAD still binds `(user_id, stream, writer_id, writer_counter)` so a blob cannot be replayed across positions, streams or users. Verify by attempting each replay in a test.
- [ ] **Step 3:** The hash chain must still verify over sealed bytes — a sealed blob's chain position is unchanged.
- [ ] **Step 4:** Commit.

### Task 4: Migration

**Files:** `cmd/ledgerd` (a subcommand), plus whatever the client needs. Tests alongside.

The spec commits to migrating rather than wiping. There is one real user with a handful of ops, so this is the cheapest it will ever be — and the path must work for every later alpha.

- [ ] **Step 1:** Replay the plaintext op log into a **fresh sealed log** under a dedicated `migrator` writer — new ciphertext, new counters, new chains — then destroy the old log. Do not attempt to seal in place.
- [ ] **Step 2:** **Verify before destroying.** The sealed log must fold to a state byte-identical to the plaintext log's, checked programmatically, before anything is deleted. A migration that cannot prove equivalence must abort and leave the original untouched.
- [ ] **Step 3:** Take a database backup first, in the same command, and say where it went.
- [ ] **Step 4:** Test against a copy of the real database, never the live one.
- [ ] **Step 5:** Commit.

## Alignment items for the operator

1. **The onboarding copy will not say "only you can access it"** — it is false, §2 forbids it, and it is a privacy claim to people signing a consent document. The replacement is stronger and survives scrutiny. This reverses an explicit instruction.
2. **Migrate rather than wipe** commits us to keeping a re-sealing path working for every future alpha.
3. **The recovery phrase is mandatory at signup.** A browser has no Keychain; skipping it means an unrecoverable account. This is friction the native design did not have, and it is not optional.
