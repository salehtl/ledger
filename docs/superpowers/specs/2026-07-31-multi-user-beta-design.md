# Multi-user closed beta — v2 architecture design

**Date:** 2026-07-31
**Status:** Approved design, revised after three adversarial reviews (third review: converged; edits applied); pre-implementation
**Supersedes:** the single-user architecture in `budgeting-app-build-plan.md` for the v2 track. The single-user instance keeps running from `main` untouched until migration (see Rollout).

## 1. Goals, in priority order

1. **Privacy & security.** Users own their data. A server breach must yield data that is as worthless as possible to the attacker. Claims must be honest and technically precise — no marketing overreach.
2. **Minimal operational cost.** No unnecessary compute. Procedural, deterministic solutions over AI. One VPS (plus a minimal relay VPS) for the foreseeable future; a dedicated cheap DB host only when scale demands it. Fixed costs accepted for the beta: Apple developer account ($99/yr), one domain, backup-relay VPS (~$5/mo).
3. **Performance.** The app must feel instant. Structural speed (local-first) over optimization.

Non-goals for the beta: AI anywhere in the pipeline, Android, banks beyond the templated set, public availability.

## 2. Honest threat model (adopted verbatim into the privacy page)

**The claim is "encrypted at rest with a plaintext ingest window" — not "zero-access", not "we can't see it."**

- Transaction emails necessarily arrive at our servers in plaintext (SMTP). They are parsed **in memory** and sealed to the user's public key at the moment of arrival; only ciphertext is stored. **The backup relay (§3.2) does not do this yet, and saying it did would be the one kind of error this page exists to avoid.** In Phase 1 the relay writes every message it accepts to its own disk **in the clear**, exactly as the bank sent it, and holds it there until the primary is reachable again — each spooled message carries a `"sealed": false` record beside it, so the phase is a fact on disk rather than a claim in a document. Sealing at the relay is Phase 3 work (the address replica already carries the account public key it will need, and the relay cannot use the primary's op-log envelope for it — see §3.2), so until then the plaintext spool window is **disclosed** in the unencrypted-surfaces bullet below rather than claimed away here.
- A stolen disk, stolen backup, seized server, or subpoena of stored data yields: ciphertext blobs; blob timestamps and size-buckets; op-type flags (that *something* was ingested/edited, not what); the unencrypted parse-diagnostics ledger (itemized in the next bullet); the aggregated `smtp_rejections` day/reason/count table (protocol-level refusals, not user-linked); pseudonymous sign-in identifiers; inbound-address tokens; the server-stored wrapped-key blobs — **the recovery-phrase wrap is high-entropy and effectively unguessable; the opt-in passphrase wrap is subject to offline guessing and is only as strong as the passphrase** (Argon2id-hardened; strength-checked at creation; the default recovery path is the recovery phrase).
- **What the parse-diagnostics ledger actually contains, field by field.** It is unencrypted by design (§3.5) and this is the complete list, not a summary. Per ingest: `user_id` (whose mail this was; NULL only for a protocol-level refusal that never resolved a recipient), `event` (`arrival` or `reprocess`), `ingest_id` (a SHA-256 of the raw body — one-way, but an operator holding a candidate message can confirm that message was ingested), `received_at` (**when**), `sender_domain` (the verified signing domain, or the envelope domain marked `unverified:`), `dkim_result` and `arc_result` (whether the signature and any forwarding chain validated), `inner_origin_domain` (**which bank, behind a forwarder** — recorded only when an attestation actually proved it), `template_id` and `template_version` (which parser was tried), `normalizer_version`, `matched` (did it), `empty_groups` (**the names of the template fields that failed to extract** — which parts of the mail we could not read), `tier` (`template`/`heuristic`/`none`), `body_size_bucket` (the padding rung, never the exact size), `structure_sig` (a content-free 128-bit fingerprint of the mail's *layout* — same layout with different amounts and merchants gives the same value), `outcome` (what happened to the message) and `reject_reason` (a closed set: `too_large`, `unknown_rcpt`, `over_quota`, `no_text_part`, `normalize_error`). **Plainly: a breach reveals which bank each user uses, when each transaction occurred, what shape their bank's mail has, and which parts of it we failed to read — but no amount and no merchant.** No subject, no From display name, no header value, no capture-group *value* and no body fragment is stored, and the database refuses to store one: every text column is constrained to a closed enum, a hostname, an identifier, or a hex digest.
- **Six further unencrypted surfaces, disclosed for completeness.** Three are in the database on the primary: the merchant dictionary (§3.6), the donated-sample queue `donated_samples` (§3.5 — the only *table* in the system that holds your mail in the clear on purpose, and only when you explicitly donate one), and `parse_rate_adjudications` — a Phase-1-only operator classification of unparsed mail, used to measure the parse rate honestly, deleted at the Phase 3 cutover. **The other three are files on the backup relay's disk (§3.2)** — a second host that has no database at all and holds nothing else about you: (a) **the spool**, every message the relay accepted while the primary was unreachable, held in the clear until the primary takes it (Phase 1; see the first bullet); (b) **the rejection lane**, messages the relay accepted and the primary then refused, which are *never deleted* — the sending mail server was already told the message was delivered, so nothing else will ever retry it, and a queue nobody looks at is a silent drop with extra steps; and (c) `addresses.json`, the relay's replica of the live inbound addresses, which it needs in order to refuse mail for addresses this system does not serve, and which is therefore a list of bearer capabilities (see the inbound-address bullet below). **No database purge reaches any of the three.** Deleting your account (§3.10) clears the primary's tables; it cannot clear another host's disk, so mail of yours sitting in that spool or that lane outlives it until an operator removes it by hand. That is an open operator decision rather than a solved problem (tracked in the project's NEEDS-SALEH log, §4). As of 2026-08-01 no relay host is provisioned, so all three are empty — this is disclosed now because it must be true *before* the relay carries real mail, not after.
- **What the merchant dictionary actually contains, field by field.** It is two unencrypted tables, and this is the complete list. `dict_entries` is the dictionary itself, and its approved rows are *published to every client by design* — it holds `pattern` (a merchant string, e.g. `carrefour`), `match_type` (`contains` or `exact`; never a regex), `category` (a short label like `groceries`), `source` (`crowd`, or `operator_seed` for the operator's own imported v1 rules), `distinct_submitter_count` (how many different people submitted it — a count, with nothing left of who they were), `approved` (the operator's moderation decision, or unset for "not yet reviewed"), `moderator_note` (the operator's own words, never a user's, never served to a client), `version` (the cursor clients page by) and `published_at` (when it first shipped). **A breach of `dict_entries` reveals the dictionary — which is public by construction — plus the pending rows: merchant patterns that somebody in the beta submitted and that have not been published, with no indication of who.** `dict_submissions` is the counting table and the only one that touches a person: `pattern` and `category` (which entry the submission is for), `created_at` (**a whole UTC day, never a precise time** — used solely to expire identifiers that never reach the threshold; it is deliberately coarse because full-precision arrival times would cluster one person's submissions together and undo the unlinkability the salt provides), `key_epoch` (an 8-byte fingerprint of *which generation of the server key* wrote the row, so the system can refuse to count or to claim erasure across a key rotation — it says nothing about the user) and `submitter_hmac`. **There is deliberately no `user_id` column in either table** — a table of (user, merchant) pairs would be a per-user merchant ledger, which is precisely what §3.6 forbids and what the rest of this page promises does not exist.
- **The `submitter_hmac` caveat, stated plainly.** It is a keyed pseudonym salted by the entry, so a stolen disk without the server key yields nothing, and one user's rows under two different merchants cannot be matched to each other. But at closed-beta scale **the operator can enumerate its own small user list against that HMAC** and recover who submitted a pattern, for as long as the row exists — so it is a bounded but real linkage between a user and a submitted merchant pattern, not a cryptographic guarantee. What will bound it is lifetime: an identifier is to be stored only while the count can still change an outcome, deleted the moment an entry reaches the k=3 threshold (before publication, not at it), never stored at all for an entry that has already reached it or that the operator seeded, and expired outright by a sweep that runs hourly in the server process if the entry never reaches the threshold at all. Submitting to the dictionary will be opt-in; declining it means no row about you exists here at any point. **Not yet true, and stated in the future tense for that reason: there is no submission endpoint until the Phase 2 client (§5), so in the alpha `dict_submissions` is empty, every dictionary entry is `operator_seed`, and no identifier about any user is written here at all.** The retention sweep and the deletion path are built and running; what has not shipped is the route that would give them anything to act on, and it is held back deliberately until it carries a rate limit and a per-user entry cap.
- **What the donated-sample queue actually contains, field by field, and for how long.** `donated_samples` (§3.5) is the one table in v2 that holds a real email in the clear on purpose. It has two shapes of row and the *default* one holds no content at all. A **structural report** — what the app sends by default when a message will not parse — is `user_id`, `sender_domain` (the cryptographically verified signing domain, never an envelope claim), `structure_sig` (the same content-free 128-bit layout fingerprint the diagnostics ledger stores: same layout with different amounts and merchants gives the same value), `created_at` and `expires_at`, and that is the whole row: `raw`, `ingest_id`, `received_at`, `consent` and `consented_at` are all empty on it, and there is at most one such row per person per format. A **donation** — a separate, explicit act, invited during setup with an in-app preview showing exactly what will be sent — additionally holds `raw` (**the message itself, in full, unencrypted**), `ingest_id` (the SHA-256 that identifies which of your messages it is), `received_at` (when it arrived), `consent` (the identifier of the consent text you were shown, e.g. `donate-sample-v1` — never your words or ours) and `consented_at` (when you agreed, from the server's clock). The server never accepts an uploaded body: it copies the message out of your own stored mail, so nothing can be filed under your name that you did not actually receive, and it takes the sender domain from its own verification record rather than from the request. **Neither shape of row takes any of that from the app.** Both name one of your own messages by its `ingest_id`, and the server fills in the bank and — for a report — the layout fingerprint from what it recorded when that message arrived, so no account can file a row under a bank it does not use, and the app cannot decide what a report says about you. **Plainly: a donated sample is a complete email of yours — amounts, merchants, card digits, everything in it — readable by the operator for as long as it is stored.** What bounds it is retention and access. Every row is deleted **180 days** after it is written (`expires_at`, swept automatically); deleting your account deletes them immediately; the operator can retire any sample at any time; and the whole table is dropped at the Phase 3 cutover. No HTTP endpoint anywhere in the system returns a donated body — the admin console replays candidate parsers over the corpus and sees only *matched / did not match* plus the names of the fields that failed to extract, and the queue view sees only counts — so the access is the operator with a shell on the box, which is stated here rather than left to be inferred from the absence of a route.
- **The inbound address is a bearer capability, and that is a property of the design.** Anyone who learns a user's `u-<token>@in.<domain>` can inject *genuinely DKIM-signed* bank mail from their own bank account into that user's ledger. The signature proves the bank sent it; it does **not** prove the bank sent it *to this user*. The mitigations are address secrecy (128 bits of entropy, RCPT-time rate limiting and tarpitting), in-app rotation with a grace window, and the review queue — **not cryptography**. Any mail-slot design has this property; it belongs in the threat model rather than being discovered later.
- A **live, actively compromised server** could log plaintext of *future* mail as it arrives, and can fabricate server-ingested transactions (§3.3 states what the integrity chains do and do not prove). It can also, without breaking any integrity claim, choose which of a user's own FX rates a given transaction freezes against, or withhold a `rate_set` from one device — `seq` is server-assigned, sits outside every writer's hash chain and outside the AAD, and the ordering between a device's `rate_set` and the ingest writer's `txn_ingested` is constrained by neither writer's own chain (§3.3, §3.7). This is bounded — it can only select among rates the user actually set, never fabricate one — but it is a new capability this design creates, not one v1 had. This is the same residual trust Proton Mail carries for external mail, and we state it plainly.
- Sign-in identifiers are pseudonymous at best (hashed, but low-entropy and enumerable; Google additionally holds the `u-xxx ↔ identity` mapping because the user configures forwarding inside Gmail). Assume a breach reveals *who* the users are; the protection is over *what they spent*.
- **Third parties:** Apple/Google learn who signs in and when (identity providers); Expo and Apple's push service observe notification timing, which correlates with transaction timing — we send content-free pushes immediately rather than delaying them, and disclose this. **For users with iCloud Keychain enabled, Apple custodies a synced copy of the device wrap key — an Apple-ID compromise is therefore part of the key-recovery threat surface.** No third party ever receives mail content.
- Metadata mitigations (required, not optional): blob padding to size buckets (1 / 4 / 16 / 64 / 256 / 512 / 1024 KB — the ladder was extended past the original 64 KB top because the measured corpus's largest compressed body is ~314 KB, and a body that fits no bucket cannot be stored at all; Decision 7), jittered/batched client-blob upload timing. (FX is manual for the beta — §3.7 — so there is no server-side rate distribution surface at all, and the per-pair travel-history side channel a live FX feed would open cannot exist; if/when automated rates land post-beta, the full-table-only distribution constraint — never per-pair queries — must be reinstated.)
- **Drop policy:** v1's "nothing is ever silently dropped" survives in v2 as **"nothing is dropped without a user-visible notice"** — quarantine expiry is warned about before it happens, and dedup collisions become review items, never silent discards (§3.2, §3.3).
- Regulatory posture: users' financial data falls under UAE PDPL (Federal Decree-Law 45/2021) and, for EU testers, GDPR. Export and deletion rights are honored in-product (§3.10); the operator is data controller for the unencrypted metadata above. Counsel consult items are tracked in §6.

## 3. Architecture: blind mail-slot server, local-first client

Still one Go binary on one VPS, plus Postgres. The server's job shrinks to: receive, parse-in-memory, seal, append, notify. The client (Expo app) holds decrypted data in local SQLite and does **all** budget math, insights, filtering, review-queue, and categorization on-device. Every screen reads local data → instant UI, offline-capable; sync is background reconciliation, never a spinner.

### 3.1 Server surfaces

| Surface | Port / binding | Purpose |
|---|---|---|
| SMTP receiver | :25 public (MX on `in.<domain>`) | Inbound bank mail per user |
| HTTPS API | :443 public, autocert | Auth, sync, template distribution, push registration |
| Admin console | Tailscale-bound only | Template authoring/publishing, donated-sample queue, diagnostics, waitlist |
| Postgres | localhost only | All server state |
| Backup relay | second VPS, :25 public (lower-priority MX) | Same binary in relay mode (§3.2) |

Exposing :443/:25 publicly is a deliberate posture change from the Tailscale-only single-user system; admin stays tailnet-only.

### 3.2 Ingestion (SMTP, self-hosted)

- Each user gets a unique inbound address `u-<token>@in.<domain>`. **Token: ≥128-bit (26-char base32), rotatable in-app.** Rotation consequences are surfaced in the rotation UX: it breaks the user's existing Gmail forward rule and any bank-side registration (both must be redone via a guided re-onboarding flow). The old address keeps accepting for a 7-day grace window; during the grace, mail from origins that were allowlisted on the old address retains trusted status and push.
- Users either point their bank's alert email directly at their address, or set an auto-forward rule in their mailbox. Gmail's forward-verification email arrives at our server; the confirmation link is surfaced in-app during onboarding.
- Receiver: `emersion/go-smtp`. Unknown RCPT rejected at RCPT time **with per-IP invalid-RCPT rate-limiting and tarpit delays** (rejection is an enumeration oracle otherwise). DATA capped at 1 MB. Per-address rate limit ~50 msgs/day (bank alerts are single digits/day; excess is an attack).
- **Origin trust** (the inbound address is otherwise an unauthenticated write endpoint into a financial ledger, and Gmail forwarding rewrites the envelope sender — SRS — so SPF-based filtering is unavailable by design):
  - The server **cryptographically verifies DKIM and ARC signatures** on every inbound message (e.g. `go-msgauth`) — header fields are never trusted unverified.
  - **Trusted-lane promotion requires a verified signature.** The allowlist entry is the *verified signing domain* plus, for forwarded mail, the **inner origin** (original From + inner DKIM domain where the forwarder left it intact) — trusting the bank, not merely the user's forwarder. Mail matching only an envelope pattern, or carrying no verifiable signature, stays quarantined permanently.
  - **Allowlist learning is explicit:** the first mail from a new origin lands quarantined; the client's "trust this sender" sheet shows the **verified signing domain — or a prominent "unauthenticated" state** — so the decision is never made from attacker-rendered content alone. Confirming promotes the verified origin via an authenticated API call. Onboarding treats confirming the first real bank email as a step.
  - **Quarantined mail lives outside the op log**: a separate, chain-free, TTL'd store with its own sync channel feeding the client's quarantine lane. Quarantined blobs never trigger push (no notification-spam channel) and expire after 30 days — **with the client warned in advance** (quarantined arrivals count as "action needed" in the watchdog; expiry is never silent, per §2 drop policy). Confirming a sender re-runs ingest for its held mail, appending the results to the op log as normal ops (they enter the integrity chains at that point).
- Processing: deterministic cascade only — published templates, then heuristic. No AI tier. **Heuristic-tier results are always flagged `needs_review` in v2, never auto-trusted** (the current heuristic is UAE/AED-shaped and must not silently enter foreign or promotional mail into a ledger). Parsed transaction + raw body are compressed (**compress-then-encrypt**; ciphertext is incompressible), sealed to the user's public key (§3.4), appended to the op log, plaintext discarded. Unparseable mail: same treatment, `unparsed` flag (a flag is all the server knows).
- **Availability:** sender MTAs retry for ~1–3 days, then bounce — and Gmail auto-disables forwarding rules after sustained failures, silently and (to us) invisibly. Mitigations:
  - **Backup relay MX (non-negotiable): the same binary in relay mode** on a second cheap VPS, holding only a synced replica of `(inbound_address → user public key)` and whatever mail is currently spooled. Managed third-party relays are ruled out (they would read plaintext). **Built as of Task 35, and Phase 1 spools PLAINTEXT, not ciphertext.** Two things about the original "seals mail at arrival exactly like the primary" wording turned out to be wrong and are corrected here rather than left to be rediscovered in production: Phase 1 is plaintext end to end everywhere, and the relay could not produce an op-log blob even in Phase 3 — `blob.Envelope` binds the *writer counter* into the AAD, and that is a position in a per-user chain assigned by the primary under a lock at append time, so a relay that guessed one would seal every message into a position it cannot be opened at. What the relay can seal to in Phase 3 is the ACCOUNT's public key, with a standalone envelope carrying no position, which is why `user_pubkey` is carried in the replica now and left empty. The disclosure obligation therefore lands on the second branch: **§2 discloses the plaintext spool window**, the never-emptied rejection lane and `addresses.json`, and states that no account deletion reaches them. Shipping with neither the sealing nor the disclosure is not an option.
  - **Client-side watchdog:** the client alerts on "no mail in N days vs. your own baseline" — only the client knows what normal looks like.
- **Precondition (Phase 0):** confirm both VPS providers permit inbound port 25 before any of this is built. If not, fall back to a managed inbound relay and re-open §2.

### 3.3 Data model: per-user op log with event sourcing (not LWW)

Record-level last-write-wins breaks this schema's invariants (splits must sum to parent; fingerprint-dedup is currently server-enforced), silently and unrepairably under E2E. Instead:

- The per-user sync log is an **append-only op log**: immutable, encrypted operations (`txn_ingested`, `txn_categorized`, `txn_split`, `txn_edited`, `rule_added`, `rate_set`, `rate_unset`, `home_currency_set`, …). **Writers are identified**: every op carries `(writer_id, writer_counter)` chosen by its author — each device is a writer, and the server's ingest pipeline is itself a writer. The server assigns a per-user total order (`seq`) at append time; `seq` is *ordering metadata only* and is never part of the encrypted payload or AAD (an offline writer cannot know it at encryption time). **Because `seq` is assigned at append, not authored,** it is monotonic in *upload* order, not author order: an offline writer's ops always receive a `seq` higher than everything already in the log, so nothing is ever inserted behind a device's sync cursor. This makes materialization **prefix-monotone** — a snapshot's only transition is null→value, and extending the synced prefix never changes a value the fold has already produced. This is the property that makes "compute once, freeze" (§3.7) safe on a device syncing in chunks, and it is stated here because it is load-bearing and was previously left implicit.
- **Sync delivery must be gap-free.** `seq` assignment alone doesn't guarantee this: a naive `nextval()` + `WHERE seq > cursor` sync can permanently skip a row that was allocated a `seq` but not yet committed when a client reads past it, breaking the prefix-monotone guarantee above. The sync endpoint must expose only a contiguous, fully-committed prefix — a watermark held below any still-in-flight append — never a `seq` value with a possible gap behind it. Writer hash-chains (below) make a skipped op detectable rather than silent, so this isn't Critical, but §3.7's FX determinism now depends on gap-free delivery, so it is stated as a requirement here.
- **Causality: every state-mutating op names what it supersedes.** Each mutable entity (transaction, envelope assignment, rule) carries a version; an op references the entity version it was authored against. Replay applies an op cleanly when its parent is the entity's current head — so a sequential re-categorization is an ordinary edit, never a "conflict." Two ops naming the *same* parent are a true concurrent fork, resolved deterministically (latest author timestamp wins, `writer_id` as tiebreak — favoring the user's later intent, since all client writers are the user's own devices) and **surfaced as a notice**, never silently. Fork resolution sets only the **going-forward head** from the winning op's `seq` position onward — it never retroactively rewrites what an earlier position's head was, nor any state already frozen against that earlier head. Because resolution is deterministic over the total order, every replica converges without an arbiter. **FX rate is deliberately not in the entity list above.** An FX rate has no "edited against a stale version": a user typing a new value asserts a new current rate, not a correction to version N, and there is no cross-field invariant like "splits sum to parent" to protect. It is modeled as a parent-free, append-only series instead of a versioned entity — see §3.7.
- **Dedup is by ingest identity, not parse output.** Every `txn_ingested` op carries the ingest ID (hash of the raw body); reprocessing after a template fix emits a *supersede* op keyed by the same ingest ID; replay keeps at most one live transaction per ingest ID. This survives template revisions that change extracted fields — the exact case reprocessing exists for. The parse fingerprint (`last4|amount|direction|merchant|day`) is demoted to a secondary heuristic for cross-source duplicates (e.g. email + CSV import): fingerprint collisions become **review items** ("possible duplicate"), never silent drops — genuine same-card same-day duplicate purchases exist. (A supersede's FX snapshot is recomputed fresh at its own log position, never inherited from the row it replaces — §3.7.)
- **Ops carry a schema version.** Clients never write op versions newer than they understand; on encountering an unknown *newer* version during replay they hard-stop sync and require an app upgrade. **Undecryptable blobs do not hard-stop**: they are set aside with a visible warning (hard-stop is reserved for chain breaks and unknown-newer versions).
- **Blob batching and the honest size math.** Client writers accumulate ops and upload them as padded blobs (buckets 1 / 4 / 16 / 64 / 256 / 512 / 1024 KB, per §2); AAD binds `(user_id, stream, writer_id, writer_counter)` at the blob level; ops carry intra-blob indices. **The ingest writer cannot batch** — it seals each email at the moment of arrival — so ingest ops are singleton blobs in the 1 KB bucket. A 3-year, ~3,700-transaction history is therefore **~4 MB of hot blobs and ~3,700 HPKE opens on restore** (measured corpus, one user, two banks); Phase 0's replay spike must model *per-op singleton blobs*, not one pre-batched file. Rich push (later, §3.8) decrypts the latest hot singleton (≤1 KB), never the cold stream.
- **Hot/cold split** — structural, from day one: *hot stream* = parsed-transaction ops; *cold stream* = raw email bodies (~25 MB/user/year, measured on one user — assume multiples for busier banks). Cold syncs lazily/on-demand; clients keep a rolling window (e.g. 90 days) locally. Client-side reprocessing pulls the cold ranges it needs.
- **Integrity chains, with precise claims.** (a) Each *client* writer hash-chains its own blobs (`writer_counter` N embeds the hash of N−1); the server cannot forge these (it lacks the DEK), so a server that drops or reorders a device's ops is detected by that device and, at sync, by the user's other devices. (b) The *ingest* writer's chain is computed by the server over material the server itself seals — **it proves storage/backup integrity and nothing about operator honesty; a compromised server can fabricate well-chained ingest ops.** The client UI therefore distinguishes server-ingested from user-authored provenance. (c) **Writer-roster checkpoints:** client writers periodically embed a checkpoint op listing every known `(writer_id → chain head)`; a fresh device verifies the server-supplied writer roster against the latest checkpoints, so the server cannot silently omit a whole writer at bootstrap. The cross-device comparison code (§3.4) covers key-history *and* checkpoint heads — computed on-device, and, like the rest of the key UX, arriving in Phase 3 (§5); the server's part, serving both inputs, is in place.
- **Cold-stream verification under lazy sync:** clients persist verified chain heads; the server serves the compact per-blob hash list, which a client verifies contiguously against its pinned head once; thereafter any range fetch is checked against its pinned per-blob hash. Reprocessing never parses an unverified cold body (otherwise a malicious server could swap a cold body and launder a poisoned transaction through the client's own trusted writer chain).
- **Snapshots/compaction: deferred deliberately.** Replay cost is acceptable at beta scale; revisit when a user's log exceeds ~50k ops. Deletion is handled by crypto-shredding, not log rewriting (§3.10).
  - **Prerequisite for ever undeferring it.** The two mandated executors (§3.5) do *not* produce byte-identical JSON for the same op: Go's `encoding/json` escapes `<`, `>`, `&`, U+2028 and U+2029 as `\uXXXX` where `JSON.stringify` emits them literally, and Go's RFC3339Nano trims trailing zeros where `toISOString` pads to three digits. That is harmless *only* because *each blob is encoded exactly once, by its author*, and the chain hashes the bytes as stored — so the two encoders never have to agree byte for byte. This is a property of how the system is used, not of the code: **the moment anything re-encodes an op it did not author — compaction, a snapshot rewrite, a migration that re-serializes — byte-inequality stops being cosmetic and becomes a chain break**, and which executor performed the rewrite decides whose chain survives. Any such work must first make op encoding byte-canonical across both languages (or re-chain deliberately from the rewrite point). Verified as of Task 10: nothing re-encodes a foreign op — `Reprocess` appends a new supersede op rather than rewriting one.
  - **What replay state compaction would also have to reclaim (Task 11).** The fold's entity-head registry is never pruned: a superseded transaction keeps its head entry forever, because a supersede does not end the predecessor's version line — an offline device's `txn_categorized` authored against the retired row still arrives, still has to resolve against a head, and an entity's applied versions have to stay contiguous for the life of the log. So the head registry grows with the log rather than with the *live* transaction count, and a user whose ingest pipeline supersedes heavily (a template revision replays every affected email) accumulates heads faster than rows. Acceptable at beta scale for the same reason full replay is, and named here so undeferring compaction treats it as in-scope rather than discovering it: reclaiming a head is only safe once no op naming that entity can still arrive, which is a statement about writer chain heads, not about the entity.

Postgres tables (server side): `users`, `sessions`, `inbound_addresses`, `op_log (user_id, seq, stream, writer_id, writer_counter, type_flag, ciphertext, size_bucket, created_at)`, `quarantine (TTL'd, chain-free)`, `templates`, `donated_samples`, `parse_diagnostics`, `waitlist`, `push_tokens`. (No server-side `fx_rates` table: FX is manual and client-side for the beta — §3.7 — rates travel as encrypted `rate_set` ops in `op_log` like any other user state, not as a distinct server table.)

### 3.4 Cryptography

**Key inventory** (every key, where it lives at rest, what it does):

| Key | Type | Lives at rest | Purpose |
|---|---|---|---|
| User ingest keypair | X25519 | public: server; private: client, wrapped | Server HPKE-seals ingest blobs to it |
| User DEK | AES-256-GCM | client, wrapped | Encrypts client-authored op blobs |
| Per-device identity keypair | signing | device Keychain (not synced) | Authenticates writer registration; subject of TOFU pinning + key-history log |
| Device wrap key | symmetric | iOS Keychain, **iCloud-Keychain-synced** | Wraps ingest-private + DEK on this device family |
| Passphrase wrap (opt-in) | Argon2id-derived | server (opaque blob) | Any-device recovery; offline-guessable — disclosed in §2 |
| Recovery-phrase wrap | high-entropy derived | server (opaque blob) | Default recovery path; unguessable by construction |

- **Two data paths, because the server writes but must not read:** ingest blobs are HPKE-sealed to the user's public key (this is what makes "parsed in memory, only ciphertext stored" implementable — a symmetric-only design would require the server to hold the data key); client-authored blobs use the DEK.
- **Wrap rotation vs. key compromise:** wrap rotation (lost passphrase, revoked device) = re-wrapping two small keys, never re-encrypting history. A compromised *key itself* (extracted from a stolen unlocked device) cannot be rotated away for history: new epoch keys cover future blobs, old keys are retained read-only, background re-encryption is an explicit non-goal for the beta.
- **Recovery forks, stated:** with iCloud Keychain on, a new iPhone on the same Apple ID restores the device wrap automatically (Apple's custodial role disclosed in §2) — it does *not* bootstrap blind from our server. With Keychain sync off — and on future Android — device loss means recovery phrase (or opt-in passphrase) or the history is gone. Re-forwarding from the user's own mailbox is not a real recovery path (Gmail has no bulk-forward) and is not marketed as one.
- **Key transparency, with its limits stated:** per-device identity public keys are TOFU-pinned by peer devices, and the server maintains an append-only key-history log per user, **served to the account it describes at `GET /api/v1/key-history`** — entries oldest-first, so the last one is the head. The server deliberately does not compute the comparison code: it is the party being audited, so the digest is derived on-device over the log a device fetched itself. **What has shipped is the server half.** The on-device pinning, the halt-and-warn and the comparison-code UX below land with the key work in Phase 3 (§5). On a history mismatch or writer-chain break, the client **halts sync and shows a non-dismissable warning**. A brand-new device with no prior state necessarily bootstraps from the server, so the key-backup UX includes a short **cross-device comparison code** — a hash over the key-history head *and* the writer-checkpoint heads (§3.3) — surfaced during second-device enrollment. Single-operator infrastructure cannot make key substitution impossible, only detectable; §2 says so.
- **Capability rules (a session token alone is not enough):** registering a new writer requires proof of key possession (a challenge sealed to an enrolled key) and is recorded in the key-history log — a stolen session token cannot inject a writer whose ops other devices would replay. Account deletion (§3.10) and address rotation require fresh IdP re-authentication *plus* an on-device confirmation backed by key possession.
- GCM with per-blob random 96-bit nonces; AAD binds `(user_id, stream, writer_id, writer_counter)` (§3.3) so blobs cannot be replayed across positions, streams, or users.

### 3.5 Templates as data + intake pipeline

Bank support at launch: the **three** existing corpus-validated parsers — DIB (Arabic), ENBD transactions (English), and ENBD account alerts (`enbd_alert.go`) — ported into the template store. Growth is via intake, not AI.

- **Store:** `templates(bank, sender_pattern, version, definition, status: draft→testing→published)`. The definition is a deliberately simple declarative format: label anchors + regexes + typed fields (amount, direction, merchant, date, currency, locale).
- **The normalization pipeline is part of the template contract.** Templates match *normalized* text, and today's normalizer (`internal/parse/body.go`: MIME part selection, charset decode, quoted-printable, HTML-strip to newlines, entity decoding, whitespace collapse) is where template behavior actually lives. It is specified as a **versioned algorithm** with its own conformance fixtures; templates declare the normalizer version they target.
- **Two executors, one constrained dialect.** Go (server, at ingest) and TypeScript (client, local reprocessing) both implement the normalizer + template executor. Template regexes are restricted to a defined **RE2-compatible, backtracking-safe subset**, validated at publish time — this both sidesteps Go/JS regex divergence (`\s` ASCII vs Unicode, case-folding differences; normalization must fold `&nbsp;`/U+00A0 explicitly) and prevents a published template from ReDoS-ing clients on adversarial mail (the inbound path is attacker-writable). A shared conformance fixture suite runs against both executors in CI; disagreement fails the build.
- **Seed validation:** ported templates must reproduce the existing three parsers' output over the full 3-year corpus before Phase 1 ships.
- **Intake flow:**
  1. Onboarding asks the user's bank. Supported → proceed. Unsupported → waitlist + invitation to donate one sample email *during setup* ("we need one example to learn your bank"), with a client-side redaction preview showing exactly what will be sent. Consent at setup converts; consent at the moment of failure does not.
  2. In operation, unparsed mail lands in the client review queue with per-email "donate". By default the client reports a **content-free structural fingerprint** (`structure_sig`: tag skeleton, label positions, zero values) so the admin console clusters demand ("14 users hitting an untemplated FAB credit-card format") without seeing content.
  3. Admin console: donated samples queue → author template → validation replays it over every donated sample for that sender → publish bumps the store version.
  4. Clients pull new template versions and **reprocess locally** over their decrypted, chain-verified cold-stream bodies; recovered transactions enter the op log as supersede ops keyed by ingest ID (§3.3), so revised parses replace — never duplicate — the originals. "Fix the parser, backfill" survives E2E at zero server compute.
- **Diagnostics (deliberate, bounded privacy concession):** per ingest the server stores *non-content* facts unencrypted: template ID attempted, matched/not, which named capture groups were empty, body size bucket, sender domain, parser version. This turns "unparsed, cause unknown" into a fixable bug report. It is also a per-user bank-and-timing ledger, and §2 lists it in the breach inventory; accepted and disclosed.
- Known fragility, accepted with eyes open: existing templates are newline-anchored regex over normalized text; Gmail forwarding re-flows HTML and applies quoted-printable wraps. Phase 1 runs *unencrypted with friendly alphas* precisely to catch this with full visibility.

### 3.6 Categorization (no LLM)

- Global anonymous merchant→category dictionary: seeded from the operator's existing rules and, **from the Phase 2 client onward** (in the alpha it is operator seed rows only — there is no submission endpoint), grown from **opt-in** confirmations (a bare merchant pattern, never user-linked). **Submissions are operator-moderated before publication, and entries are suppressed until at least k distinct users have submitted the same merchant** — this blocks both dictionary poisoning (`AMAZON → Charity`) and rare-merchant entries that would be user-identifying. Distributed to clients like templates.
- Per-user override rules live client-side and sync as encrypted ops. Rule matching runs on-device.

### 3.7 Currency & FX (manual for the beta)

- **Manual, not automated — the beta generalizes v1's rate mechanics (integer micro-rate, snapshot-on-first-rate, backfill-on-later-rate) from a hardcoded AED base to a user-chosen home currency, rather than integrating an upstream FX API.** ("Reuses wholesale" overstates it — see home-currency handling below, which is new.) This removes a whole server surface from the critical path: no daily upstream fetch, no full-table distribution mechanism, no cached historical-rate binary, and no exposure to the unresolved third-party redistribution-ToS question (below). Every transaction stores its original currency + amount in that currency's minor units (`int64`).
- **Home currency is log state, established by an onboarding op (§3.9) — never a device-local setting.** Two devices must agree on the home currency to compute identical snapshots from the same log; a per-device preference would reproduce the exact silent divergence §3.3's op log exists to prevent.
- **Immutable after onboarding, for the beta.** `rate_micro` is *home units per foreign unit*; changing the home currency after the fact would invalidate every stored rate's meaning and re-denominate every already-frozen snapshot in the log. v1 never faced this — AED was hardcoded, not a variable — so this is a genuinely new constraint the beta accepts rather than solves: the picker is one-shot at onboarding with no in-product way to change it afterward. A post-beta change means a re-denomination migration (replay the log, re-freeze every snapshot under the new base, re-enter every rate) — not a settings toggle.
- The client — never the server — holds a per-currency rate table: `rate_micro` (home-currency units per 1 foreign unit × 1,000,000) plus `updated_at`. The home currency itself carries no rate row (implicit identity, `rate_micro = 1_000_000`), same as v1's AED. Rates are entered/edited by hand in a Currencies settings screen, mirroring v1's screen and its inline fixer for missing rates. The seeded USD peg (v1: 3.6725, fixed since 1997, `internal/store/fx.go:26-33`) becomes a real `rate_set(USD, 3672500)` op written at onboarding rather than a schema default — and it is only a sane default for AED-home users; other home currencies onboard with no seeded rates.
- **Conversion:** `(amountMinor * rateMicro + 500_000) / 1_000_000`, half-up — identical to v1's `ConvertToAEDFils` (`internal/store/fx.go:21-23`), generalized from AED to "home currency." **"Integer so conversion never touches floats" is a Go guarantee; it does not hold for the TS executor as written** — `amountMinor * rateMicro` exceeds `2^53` for realistic amounts in high-rate or zero-decimal currencies, silently losing precision under plain `number` arithmetic. The TS conversion path must use `BigInt`, or the safe range must be proven and documented; either way this joins §3.5's Go/TS conformance suite.
- **`rate_set` is parent-free and append-only — deliberately not a versioned entity like the others in §3.3.** A rate has no "edited against a stale version": typing 3.68 asserts a new current value, not a correction to version N, and there's no cross-field invariant to protect the way splits must sum to parent. So it names no predecessor and there is no fork to resolve. "The rate for currency C at log position P" = the last `rate_set(C, …)` at or before P — a positional lookup, not a version chain. This is also cheaper for Phase 1: a parent-free op needs no head read before writing. Uniquely among §3.3's entities, an FX rate's *entire* positional history stays load-bearing — every other entity there only ever has its current head read, but a transaction snapshots against the rate live at its own position, so an old `rate_set` remains meaningful to every transaction sequenced before the next one supersedes it.
- **`rate_unset`** (v1: `DeleteFXRate`, a live trash button) is kept as an op: after an unset at position P, transactions sequenced after P see no live rate and snapshot null until a later `rate_set`; transactions already frozen before P are untouched — same non-retroactive rule as everywhere else here.
- **Snapshot semantics, preserved:** a transaction's home-currency amount is computed once — the first time a rate exists for its currency at or after the transaction's own log position — and frozen; a later edit to that rate never rewrites already-snapshotted history, but does backfill every transaction of that currency still unconverted at that point. This reproduces v1's `UpsertFXRate`/`ConvertUnconverted` behavior (`internal/store/fx.go:64,125-142`), client-side.
- **Supersede (§3.3) recomputes fresh at its own log position — it never inherits the predecessor's snapshot.** A template fix can change the parsed amount or even the detected currency (§3.2: the heuristic tier is UAE/AED-shaped, so correcting a mis-detected AED-read-as-USD is precisely a case reprocessing exists for); inheriting the old snapshot would carry a wrongly-based number forward. So §3.3's "already-snapshotted rows are untouched" means untouched **by later `rate_set` ops** — a supersede is a new value at a new log position and always computes against the rate head live there, never null-by-default and never inherited.
- **Unknown rate is visible, never a guess:** a transaction whose currency has no rate is still saved and shown in full, in its native currency, with a null home-currency snapshot. **Not every budget aggregate treats null as zero** — two v1 aggregates deliberately don't: recurring-bill detection (`internal/store/recur.go:11-16,27`) falls back to the raw foreign amount rather than zeroing, because zeroing an unconverted subscription would make its bills undetectable and unmatchable — v2 inherits this exception as-is, deliberately. Project rollups (`internal/store/projects.go:181`) fall back the same way via `COALESCE(amount_aed, amount)`, but that one is an arguable v1 bug (its comment justifies the fallback only for AED-native rows, but it also catches foreign-currency rows, mixing raw foreign minor units into an AED total) — v2 should fix this, not port it. Every other aggregate treats null as zero. The currency appears in a missing-rates list with an inline "add rate" action; v1's principle stands — a silently guessed rate is worse than a visibly missing one.
- **The op-log consequence.** In v1 the server computed the snapshot at insert, because it held both the amount and the rate. In v2 the server is blind to both — it parses in memory and seals to the user's key, never seeing amounts or rates — so rates must be synced, replayable state, not device-local cache:
  - A rate edit is its own op, `rate_set` (parent-free — see above).
  - Conversion happens **on-device, during replay/materialization** — never at ingest, since ingest is server-side and the server must not compute, or see, a home-currency amount.
  - **Determinism, stated positionally:** `snapshot(T) = convert(amount(T), head_rate(ccy(T), P))`, where `P` is the smallest log position ≥ `pos(T)` at which a head rate for `ccy(T)` exists in the synced prefix; null if no such position exists yet. `head_rate(ccy, P)` is the last `rate_set`/`rate_unset` for `ccy` at a position ≤ P, resolved purely by fold-by-`seq` (§3.3) — never by wall clock or author timestamp, since a parent-free `rate_set` has no fork to arbitrate. Because `seq` is append-order and materialization is prefix-monotone (§3.3), incrementally applying newly-synced ops in `seq` order is provably equivalent to a full re-fold from position 0: a device that syncs in ten chunks and one restoring from scratch compute identical snapshots for every transaction, satisfying §3.3's no-arbiter convergence requirement.
  - A later `rate_set` for a currency, replayed at a later position, backfills every transaction of that currency whose snapshot is still null *as of that position* — and only those; already-snapshotted rows are untouched (per the supersede scoping above).
  - This is deliberately not a historical rate time series: like v1, there is one current rate per currency at any position, and "current" means "latest `rate_set` at or before this position," not "the market rate on the transaction's date." A user who wants dated-rate accuracy manages it the way v1 users already do — edit the rate around a trip.
- **The stale-rate trade-off, detection and recovery.** A *missing* rate is visibly flagged (null snapshot, missing-rates list); a *stale* one is not — it silently produces a wrong-but-plausible number, visually identical to a correct one. Inherent to manual entry, accepted for the beta. `updated_at` is tracked per rate (v1 schema, reused as-is) and the client surfaces rate age in the Currencies screen (e.g. "USD set 41 days ago") with a staleness affordance — **new client work, not inherited UI**: v1's API already returns `updated_at` (`internal/server/rates.go:29,53`) but v1's own `CurrenciesPage.tsx` never renders it. Detection alone isn't recovery: "edit the rate around a trip" only helps prospectively — bank alerts land within seconds of a purchase, so a user who notices a stale rate *after* the transactions already landed has, in v1, no way to fix them (`ConvertUnconverted` only fills nulls; there is no reconvert affordance anywhere in the product). v2 adds a per-transaction **"recompute at current rate"** action, emitted as a `txn_edited` op that **carries the resulting home-currency amount explicitly in its payload** — not a pointer telling replay to recompute later — so the corrected value lives in the log and replay stays a pure function of logged data.
- **Post-beta: automated rates.** `2026-07-31-v2-open-questions-research.md` (Question 1) has completed vendor research for this — Open Exchange Rates recommended, pending one unresolved redistribution-ToS question. Picking it up reintroduces exactly the server surface this section currently avoids (daily upstream fetch, full-table distribution to clients, cached historical-rate binary, §2's per-pair-query prohibition), and reopens the determinism question above from the other direction — does a server-computed rate simply emit a `rate_set` op on the user's behalf, or does automated distribution need its own replay discipline? — worth its own design pass, not a retrofit.

### 3.8 Auth, sessions, push

- Sign in with Apple + Google Sign-In (identity only, non-sensitive scopes — no OAuth verification/CASA exposure) via `expo-auth-session`. App Store rule: offering Google obligates Apple sign-in; both ship.
- Backend verifies identity tokens, issues **opaque server-side session tokens** (revocable; no JWT machinery). Passwords never exist. Sessions alone are deliberately weak capabilities — see §3.4 capability rules.
- Push: Expo push service, **content-free** ("New transaction") for the beta, sent immediately — instant notification is core product value, and the resulting timing visibility to Expo/APNs is disclosed in §2 rather than jittered away (a "delay notifications" privacy setting may be offered later). Quarantined mail never triggers push (§3.2).
- Rich decrypted notifications later via an iOS Notification Service Extension. Honest costing: the *prebuild/custom-dev-client* cost is already sunk in Phase 2 (the JSI crypto module forces it — §3.9); the NSE's *incremental* cost is a separate process with a ~24 MB ceiling and a **second crypto implementation in native Swift** (HPKE + GCM) sharing a Keychain access group, kept bit-compatible with the JS one and pointed only at the latest hot singleton blob (≤1 KB).

### 3.9 Client (Expo, iOS-first)

- Expo / React Native, iOS TestFlight for the beta; Android later. Reuses the framework-free `lib/` logic (money, filtering, gesture predicates) and API types; screens/components are a rewrite (Reanimated, RN primitives). The JSI-native crypto module means a custom dev client / prebuild from Phase 2 onward (never bridge/base64 marshalling — measured as a cold-start killer).
- Local SQLite is the source of truth for the UI; op-log replay materializes it.
- Review queue, quarantine lane with "trust this sender" (§3.2), donation flow with redaction preview, forwarding-setup onboarding with in-app Gmail verification link, home-currency picker (one-shot, immutable — §3.7), key backup UX (recovery phrase default, optional passphrase, cross-device comparison code).
- **First-week experience (empty-state is a churn risk):** onboarding ends with a working pipeline but zero history. Phase 2 therefore includes **client-side statement import** (CSV to start; the normalization logic from `internal/importer/` joins the dual-executor conformance suite) so a new user can backfill months of history on day one, plus a deliberate "budget warming up" presentation for the first weeks rather than a blank 50/30/20 screen.

### 3.10 Data ownership: export & deletion

"Users own their data" is a product feature, not a slogan:

- **Export:** generated **on-device** from local SQLite (decrypted JSON + CSV, shared via the iOS share sheet). Trivial in a local-first design — the user's device already holds everything; the server is not involved.
- **Account deletion:** in-app, self-service (App Review guideline 5.1.1(v) requires it), gated by fresh IdP re-auth + key possession (§3.4 — a stolen session token must not be able to crypto-shred a life's financial history). Server-side it is **crypto-shredding plus purge**: delete the user's op-log and quarantine rows, wrapped-key blobs, public keys, diagnostics rows, addresses, sessions, and push tokens. Backups age out on their retention schedule; until then their copies of the user's blobs are ciphertext whose keys no longer exist anywhere.  Ships in **Phase 2**, before any external tester touches the system with crypto on.
- **Beta terms:** a plain-language ToS stating the app is informational, not financial advice; balances/budgets must be verified against the bank; and (for alphas) the Phase 1 plaintext handling, retention, and deletion commitments (§5).

## 4. Acknowledged trade-offs (accepted, not hidden)

1. **Privacy vs. cost:** E2E forbids cross-user dedup/compression of near-identical bank HTML (~an order of magnitude of storage at scale). Accepted; mitigated by compress-then-encrypt and hot/cold split.
2. **Privacy vs. performance:** cold-start cost of encrypted history — realistically ~4 MB and ~3,700 HPKE opens for a 3-year history (singleton ingest blobs cannot batch). Phase 0 validates exactly this workload; full raw-body hydration stays lazy and background.
3. **Privacy vs. supportability:** we cannot read the inputs to a failing parser. Mitigated by non-content diagnostics, structural fingerprints, consent-gated donation, and an unencrypted alpha phase to stabilize templates first.
4. **Privacy vs. immediacy:** instant push leaks transaction timing to push infrastructure. Accepted and disclosed (§2, §3.8).
5. **Bank coverage is a human bottleneck** (hand-written templates per bank per alert type). Accepted via narrow launch scope + intake pipeline + waitlist. AI re-enters, if ever, as consent-gated/user-initiated — never the always-on server path.
6. **Single-operator key infrastructure:** silent key substitution and fabricated server-ingested ops are made *detectable/attributable* (TOFU + key history + writer-roster checkpoints + provenance in the UI + comparison code — the server serves the key-history log and the checkpoints today; the on-device pinning and comparison arrive in Phase 3, §5), not impossible; a fresh device's first bootstrap trusts the server unless a prior device verifies it. Stated in the privacy page.

## 5. Rollout

Each phase has an explicit exit criterion; failing it means stop and rethink, not push on.

- **Phase 0 — kill-risks week.** (a) Confirm inbound port 25 with both VPS providers — gates §3.2. (b) Spike local-first: on-device SQLite + budget-math replay over the real ~3,700-transaction corpus **as per-op singleton encrypted blobs** (§3.3's honest workload) on the oldest target iPhone. *Exit: port 25 confirmed; cold replay + first paint within an acceptable budget (target <2s warm, <10s cold-restore) on that device.*
- **Phase 1 — backend v2, plaintext.** Postgres, auth, hardened SMTP receiver with verified DKIM/ARC, op-log sync (hot/cold, batched padded blobs, causality versions, both chains + checkpoints), quarantine store, template store + normalizer contract + conformance suite + diagnostics, backup relay. **The Phase 1 sync client is a minimal headless client** (script or bare Expo shell) that authenticates, pulls, replays, runs the invariant checker, and round-trips client-authored ops — this, not the PWA, is the exit test; the existing PWA may additionally serve alphas via a temporary server-side materialized view, understood as throwaway. 3–5 friendly alpha users, **unencrypted, under signed plain-language consent** (plaintext handling, retention limit, migrate-or-delete at Phase 3 cutover), known banks, full parser visibility while Gmail-forwarding fidelity is proven. *Exit: headless client replays cleanly with invariants green across two concurrent writers, including a supersede-after-template-fix round-trip; ≥95% of alphas' genuine transaction mail parses over two consecutive weeks; zero drops without notice (every inbound email accounted for in diagnostics or quarantine).*
- **Phase 2 — Expo app.** **First, mandatory: a native-crypto (JSI) benchmark of X25519 + AES-GCM open, on-device, over the Phase 0 corpus shape** — Phase 0's replay spike passed only *provisionally*, on pure-JS crypto that was 94.3% of a 58s median cold restore against a 10s budget; the provisional pass assumed a 10–100× native-JSI speedup (`spike/phase0/RESULTS.md`) that has never been measured. This benchmark must land, and its result checked against that assumed range, before the rest of Phase 2 is planned around crypto being fast. Then: local-first client, replay + invariant checker, review queue + quarantine lane, onboarding (bank picker, forwarding setup, "trust this sender" step), CSV import + first-week experience, export + account deletion, key UX built but crypto dormant. *Exit: the native-crypto benchmark, applied to Phase 0's cold-restore decomposition, projects a cold restore **and** first paint that both fit Phase 0's budget (<10s cold, <2s warm) on the oldest target device — a raw speedup ratio in the 10–100× range is not sufficient on its own (`spike/phase0/RESULTS.md` shows the 10× case clears the 10s gate by only ~12%, leans on a `fetchMs` the same document disclaims as unrepresentative, and excludes first paint, which Phase 0 never measured); if the projected budget isn't met, Phase 0's provisional pass must be revisited before proceeding; and a fresh install onboards, imports a statement, syncs, categorizes, and survives airplane-mode edits on two devices without invariant violations.*
- **Phase 3 — crypto on.** HPKE ingest sealing, DEK for client ops, wraps + recovery phrase, device identity keys + TOFU key history + comparison code, padding, jittered uploads. **Includes the migration tool:** replays a plaintext op log into a fresh encrypted log under a dedicated `migrator` writer (new ciphertext, counters, chains), then destroys the old log — used both for consenting alphas and for the operator's own v1 data (transactions *and* the ~75 MB `ingest_log` corpus into the cold stream, rules/splits/assignments as coherent versioned ops; fed from v1 SQLite). *Exit: end-to-end flow with crypto on matches Phase 2 behavior; restore-from-backup verifies against the server chain; second-device enrollment verifies via comparison code against writer checkpoints; one real alpha and the operator's v1 history migrated with invariants green.*
- **Phase 4 — closed beta.** TestFlight external testing (budget a Beta App Review rejection round — finance app with a mail-ingestion core loop), honest privacy page (§2), ToS (§3.10). NSE rich push and Android post-beta. *Exit: defined by beta learnings; not pre-committed.*
- **Migration:** the operator migrates onto v2 as user #1 via the Phase 3 tool; the single-user path retires afterward.

Development happens in this repo on a long-lived v2 branch/worktree; `main` keeps serving the running single-user instance until migration.
